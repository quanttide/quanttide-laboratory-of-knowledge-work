# 开发计划

实验室里的工具箱怎么长成一件成形的东西。当前阶段只在实验室内开发，不进入产物仓、规格与手册。

## 现状

```text
examples/
├── kit/            唯一入口：五个动作（find / list / check / 契约 / 案卷）
├── resolver/       契约与目录两层：contract.py（应该有什么）、catalog.py（实际有什么）
├── contract/       契约结构：目标 / 输出形态 / 必须包含 / 检查项
├── dossier/        案卷结构：产出 / 审查 / 裁决 / 成果
├── material/       材料字段确认（一次性验证，已完成）
└── default-module/ 两种模式的设计：Default 默认入口 / Work 契约约束
```

`docs/user-guide/` 是对外说明；本文件是对内计划。

## 架构原则

1. **库与入口分开**：库只接受传进来的参数（如仓库根），定位与打印都归入口；库可被别的程序复用。
2. **一个入口**：可执行的东西只有 `kit`。实验目录可以多，入口不许乱。
3. **无服务端**：文档在文件里，索引现扫现生成；没有端点、没有数据库、没有后台进程。
4. **只读**：工具不改仓库内容，写入仍由人和 AI 在对话里做，提交走 git。
5. **命名两件套**：英文文件名定路径、中文标题定概念——查得到靠这两样，不靠额外元数据。

## 待办

按优先级排列，每项带判据。

**① 砍掉重复入口**

`resolver/resolver.py` 与 `kit` 是同一套库的两个壳。删掉前者，`resolver/` 只留 `contract.py` 与 `catalog.py`。
判据：`resolver/` 下没有可执行入口；五个动作仍全部可用。

**② 补齐案卷骨架**

`kit new-contract` 已有契约模板，补 `kit new-dossier`：写出「产出 / 审查 / 裁决 / 成果」四段骨架。
判据：新文件经 `kit audit-dossier` 一次通过。

**③ 检查项从契约文件读**

现在机械核对写在 Python 里（每条契约配一段代码），适合一次性交付，不适合天天立契。让它回到契约文件：检查项里声明可执行的部分（路径存在、文件不含某段文字），由工具逐条跑。
判据：一条真实契约不写 Python 也能跑出机械核对结果。

**④ 最小测试**

给 `catalog`、`contract` 两个库加测试：用真实仓库当夹具，断言二十格齐备、按名能查到已知文档、模糊兜底命中。
判据：测试在干净检出上可跑；故意改坏一处（如临时建一个未登记目录）测试报红。

**⑤ 对账报告导出**

目录 JSON 已有；再补一份对账报告（缺哪些资产、哪些目录未登记），供别的程序读。
判据：`kit check --json 报告.json` 落出的文件包含两类问题且为空时也能被解析。

**⑥ 毕业条件**

离开实验室、进工具箱仓（`packages/quanttide-work-toolkit`）之前要满足三条：五个动作在真实仓库上稳定跑通；有测试守着；契约与案卷的格式被真实使用过至少一次（不是只有样例）。

## 不做的事

- 不做服务端、不做数据库、不做可视化面板；
- 不在实验室外改文件（产物、规格、手册一律不碰）；
- 不为「以后可能需要」提前加字段——材料四字段、契约四段、案卷四段都是够用即可，多了就是负担。
