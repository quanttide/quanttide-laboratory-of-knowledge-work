# Default 模块：知识工作技术设计

两种工作模式的技术设计。底座是仓库里的 Markdown 与目录，不引入服务端与数据库。

## 两种模式

**Default（默认入口）**：想不到放哪就放这。人零门槛写下想法，AI 后续按需加工，够用就走。

**Work（指令约束）**：任务有明确交付要求时，先把指令写全再开工——目标、步骤、验收（判据机械的跑、判断的留闸门）；AI 照指令干活，人只拍板。

## 四种记录，各有归处

**材料**：还没做成成品的输入——类型、内容、来源、时间，落在它所在的那一格。

**指令**：这个任务要什么、怎么走、怎么算合格——目标、步骤、验收；判据（机械 / 闸门）住在验收里，就是 `specification/process/task.md` 说的那份指令。

**报告**（侧重事件）：生成者产出、审查者报告、人类裁决、最终成果，落在 `data/report/`。机器可生成——审查者报告由指令的机械核对跑出，最终成果由产出收束。

**历史**（侧重叙事）：这个任务的来龙去脉，落在 `data/history/`，由人写。

## 工作流与运行

**工作流**是过程的编排定义——一串标准任务（`specification/process/workflow.md`）。本程序带的默认工作流叫「一次交付」，七个标准任务（线性，一件工件往下走）：

| 标准任务 | 干什么 | 交出什么 | 怎么算完 |
|---|---|---|---|
| 材料 | 把还没做成成品的输入记进来 | `materials.md` 一行 | 四字段（类型/阶段/时间/来源）填得出 |
| 指令 | 写下这一次的指令 | `task.md` | 三段齐全：目标 / 步骤 / 验收 |
| 核对 | 按验收跑机械核对 | 报告里的审查者报告 | 机械项有结论，闸门项列给人 |
| 产出 | 把做出来的东西记上 | 报告里的生成者产出 | 落在盘上、路径写得清 |
| 裁决 | 谁拍板、决定是什么 | 报告里的人类裁决 | 有人、有决定 |
| 成果 | 把产出收束成成果 | 报告里的最终成果 | 成果由产出收束而来 |
| 历史 | 写下这一次的来龙去脉 | 历史 | 叙事，人写 |

**运行**是工作流的一次执行——`specification/process/task.md` 说的「过程的一次执行实例」。一次运行落一处现场，记录按资产进格：

```text
runs/<名字>/        一次运行的现场：task.md（指令三段）、materials.md、log.jsonl
report/<名字>.md    事件：四段由动作写出来
history/<名字>.md   叙事：人来写
```

七个标准任务的状态由文件里的事实读出来，程序只摆出该做的那一个。人只出现在两处：写指令（目标 / 步骤 / 验收）、写历史与裁决。

## 三个角色

生成者按指令产出；审查者按验收里的判据核对，机械核对可自动化、判断留给闸门；闸门由人拍板，裁决记入报告。

## 索引与存储

记录都落成仓库里的 Markdown，按资产进对应目录；检索不靠服务，靠目录层扫描生成的名字索引——资产层（`src/kg/assets.py`）与目录层（`src/kg/catalog.py`）。

## 落地顺序

1. 指令结构化：目标、步骤、验收（判据住验收里）。
2. 报告字段化（事件）：生成者产出、审查者报告、人类裁决、最终成果。
3. 材料字段确认：类型、内容、来源、时间。
